**B2 — REDEFINED. Do not follow the spec's version of this item.**

The spec asks for a rooted-path test case to pin `FileEntityName.IsValid`'s `!Path.IsPathRooted(name)` check. **That test cannot fail, and this plan's verification pass proved it by running a program rather than reasoning about it.**

`FileEntityName.cs:12-17`:

```csharp
public static bool IsValid(string? name) =>
    !string.IsNullOrWhiteSpace(name)
    && name.IndexOfAny(['/', '\\']) < 0
    && !name.Contains("..", StringComparison.Ordinal)
    && !Path.IsPathRooted(name)
    && name.All(c => char.IsAsciiLetterOrDigit(c) || c is '-' or '_' or '.');
```

Measured on Windows/net10.0:

```
C:\foo     slash=True  rooted=True
/foo       slash=True  rooted=True
C:foo      slash=False rooted=True
foo        slash=False rooted=False
```

Both proposed inputs contain a separator, so the `&&` chain short-circuits **before** `!Path.IsPathRooted` is evaluated. Removing that clause changes nothing for either. Nor is it fixable by choosing a different string: rooted-on-Windows needs a leading separator (barred by the slash check) or a colon (`C:foo` — barred by the char whitelist); rooted-on-POSIX needs a leading `/` (barred by the slash check). **No input exists that is rooted while passing the sibling checks.** The clause is unreachable defence-in-depth.

**Do this instead:**

1. **Add the two cases anyway** — `C:\foo` and `/foo` genuinely must be rejected, and pinning that is worth doing. But do **not** claim they pin the `IsPathRooted` clause, and do **not** attempt a "remove the clause, watch it fail" control for them: it will not fail, and reporting it as a passing control would be false.
2. **Write the ruling into `FileEntityName.cs`** beside the clause: it is unreachable given the slash and character-whitelist checks that precede it, it is retained as defence-in-depth against a future reordering of those clauses, and **anyone tempted to relax the slash check must not assume `IsPathRooted` covers it** — it does not, because it never runs first.

This is the honest closure. An unreachable clause with a written reason is closed; a test that cannot fail is the defect this branch exists to remove.

### Task 5: F1 — the stray `\r` in rendered list output

**Files:**
- Modify: `src/Scrinia.Mcp/MemoryTools.Core.cs` — 20 `AppendLine` calls in `BuildSummary` (`:685-746`) and `BuildFullList` (`:795-886`)
- Modify: `tests/Scrinia.Tests/Golden/__snapshots__/list-summary.yaml`, `list-full.yaml`

**Interfaces:** none. **This is the only production behaviour change in the branch** — hence its own commit.

`MemoryList`'s builders use `AppendLine`, which emits `\r\n` on Windows, while `ToYaml` splits on `\n` only — leaving a stray `\r` at the end of each rendered line.
