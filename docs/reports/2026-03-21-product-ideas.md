# Product Improvement Proposals — 2026-03-21

Source: product-evolutionary skill first run, backlog:scrinia entries

These proposals were generated by observing friction during the evolutionary and cartographer meta-skill runs. Each proposal identifies a repeated manual pattern that could be automated at the tool level.

## PEA-001: Metadata-only update tool (`update_meta`)

**Friction:** The cartographer meta-skill enriched 22 memories with new keywords and cross-references. Each required a full show() + store() round-trip -- a read-modify-write cycle that risks content corruption if re-encoding is not lossless.

**Impact:** Keyword enrichment is one of the highest-value maintenance operations (directly improves search recall). Making it expensive discourages it. The cartographer exists specifically because this operation is too costly to do casually.

**Proposal:** Add `update_meta(name, keywords?, description?, reviewAfter?, reviewWhen?)` that modifies index metadata without touching artifact content. Implementation: update the .nmp2 header and re-index without re-encoding the payload. Single O(1) call per memory instead of a full read-modify-write cycle.

**Complexity:** Low

## PEA-002: Code-artifact drift detection (`codeRefs` + `check_drift`)

**Friction:** The evolutionary agent found multiple stale references in a single pass: arch:mcp-tools said "ScriniaMcpTools" when the class was renamed to "MemoryTools", tool count said 33 when it was 35, test counts were outdated, and architecture descriptions omitted the resilience layer. Every instance was a memory referencing a code artifact that changed since the memory was written.

**Impact:** This is the #1 source of knowledge base rot. Memories become stale not because the knowledge is wrong, but because the codebase moved underneath them. The evolutionary agent's entire job was essentially detecting this class of drift.

**Proposal:** Add optional `codeRefs` parameter to store/append that records file paths + content hashes the memory depends on. On list() or a dedicated `check_drift()` call, compare current hashes to stored ones and flag memories where referenced files have changed. Example: `store(content, "arch:mcp-tools", codeRefs=["src/Scrinia.Mcp/MemoryTools.cs", "src/Scrinia.Mcp/ProjectTools.cs"])`.

**Complexity:** Medium

RESPONSE: Implement

## PEA-003: Memory compaction tool (`compact`)

**Friction:** learn:execution-outcomes has 19 appended retrospective chunks and grows monotonically. At the current rate, this memory will exceed the 8KB MCP response limit within a few more goals. The audit:findings-registry (110 entries, 4 chunks) faces the same trajectory.

**Impact:** Append-heavy memories are the most valuable ones (journals, registries, outcome logs) but they are the ones most likely to become too large to retrieve. Today the only option is manual show-all + summarize + store-back, which destroys the granular chunk structure.

**Proposal:** Add `compact(name, strategy?)` where strategy could be: "summarize" (LLM-assisted condensation preserving key facts), "merge" (combine N chunks into fewer), or "archive-old" (move older chunks to versions/ while keeping recent ones live). Compacted version retains searchability while reducing retrieval cost.

**Complexity:** Medium-high

RESPONSE: I think the strategy is merge recent, summarize less recent, and archive old. Ensure those old memories will resurface when the connections to them are deep or at the cartographer descretion. What do you think?

## PEA-004: Reverse-reference index

**Friction:** When MemoryTools.cs was renamed from ScriniaMcpTools.cs, every memory referencing the old filename became stale, but there was no way to discover which memories those were without trial-and-error searching. The cartographer faced the same problem: building bridges required searching for each concept from multiple angles because there is no "show me everything that references X" query.

**Impact:** The knowledge base is full of forward references (memory A mentions file B, concept C, memory D) but no reverse index. Maintenance is quadratic: updating references after a rename needs O(N) searches across M possible terms.

**Proposal:** Build a reverse index during store/append that extracts file paths (*.cs, *.json, etc.) and memory cross-references (topic:name patterns) from content. Expose via `references(target)` that returns all memories mentioning the target path or memory name. This would also power drift detection (PEA-002): when a file changes, automatically identify which memories need review.

**Complexity:** Medium

RESPONSE: Implement

## PEA-005: `plan_tasks` file-conflict analysis

**Friction:** Every plan_tasks decomposition this session included manual file-conflict analysis -- listing which files each task touches, checking for overlaps, deciding between worktree isolation vs. wave sequencing. Done 8+ times across G-20 through G-23. The analysis is always the same deterministic algorithm.

**Impact:** File conflicts between parallel agents are expensive (rework, context loss, merge resolution). The analysis is mechanical -- it does not need LLM judgment. Having agents do it manually means it can be forgotten, done inconsistently, or done incorrectly.

**Proposal:** Add file-conflict analysis to plan_tasks itself. Accept an optional `files` field per task (list of file paths the task will modify). When present, plan_tasks computes overlap between same-wave tasks and either auto-adjusts waves to avoid conflicts or returns a warning with conflict details and a recommendation (worktree isolation vs. re-sequencing).

**Complexity:** Low-medium

RESPONSE: Implement
